## 一、V1/V2/V3 到底是什么

```
┌─────────────────────────────────────────────────────┐
│                                                     │
│   qcc_x86.c (编译器源码, 8023行)                     │
│                                                     │
│   ┌─────────┐     ┌─────────┐     ┌─────────┐      │
│   │  gcc    │     │  V1     │     │  V2     │      │
│   │(英文C)  │ →   │(甲言)   │ →   │(甲言)   │ →    │
│   │ 编译    │     │ 编译    │     │ 编译    │      │
│   └────┬────┘     └────┬────┘     └────┬────┘      │
│        │               │               │            │
│        ▼               ▼               ▼            │
│     V1.exe          V2.exe          V3.exe          │
│   (74MB)          (60MB)          (74MB)            │
│   gcc产物         甲言产物        甲言产物           │
│                                                     │
│   种子编译器      第一代自举      第二代自举         │
│                                                     │
└─────────────────────────────────────────────────────┘
```

三个 .exe 都是编译器。都是同一份源码 (qcc_x86.c) 编译出来的。
区别是"谁来编译"：

  V1：gcc（英文 C 编译器）编译源码 → 产出的编译器
  V2：V1（甲言编译器）编译源码 → 产出的编译器
  V3：V2（甲言编译器）编译源码 → 产出的编译器


## 二、两种"相等"，两个不同的证明

### 证明 A：H1==H2（中文对等英文）

```
同一份 C 程序 (比如 fib.c)：

  路径 H1: fib.c → 甲言编译器 → fib_H1.exe → SHA256 = abc123
  路径 H2: fib.c → gcc        → fib_H2.exe → SHA256 = abc123

  SHA256 相同 → 中文关键字不影响语义。
  整==int、若==if、返==return、构==struct。
  映射正确。AST 一样。产物一样。

  这是"甲言是C的等价格"的证明。
```

### 证明 B：自举不动点（编译器能复制自己）

```
编译器源码 (qcc_x86.c)：

  V1 (gcc编译) → 编译源码 → V2
  V2 (甲言编译) → 编译源码 → V3
  V3 (甲言编译) → 编译源码 → V4

  如果 V2==V3==V4 ... → 自举不动点。
  编译器能自己编译自己，产物一致，链不断。

  这是"甲言能自举"的证明。
```

### 两个证明测的是不同的东西

  H1==H2 测的是：中文关键字映射对不对。
  自举不动点测的是：编译器能不能复制自己。

  H1==H2 的对象是"任意C程序"。
  自举的对象是"编译器自己"。


## 三、为什么 V1!=V2 是正常的

V1 是 gcc 编译的。V2 是甲言编译的。两个不同的编译器：

```
gcc (GNU C Compiler):
  诞生: 1987年
  代码量: 1500万行
  优化: 30年积累, O2/O3/Os 多级优化
  寄存器分配: 图着色算法 (复杂)
  指令调度: 乱序调度
  产物大小: 74MB (V1)

甲言 (qcc):
  诞生: 2026年7月
  代码量: 8023行
  优化: 无 (-O0级别)
  寄存器分配: 简单贪心
  指令调度: 顺序发射
  产物大小: 60MB (V2)
```

同一份源码。两个不同编译器。产出的二进制不同是正常的。

就像两个人抄同一篇文章：
  一个人用钢笔、一个人用圆珠笔。
  字迹不同，内容一样。
  "字迹不同"不证明"文章抄错了"。

V1!=V2 不证明甲言有 bug。只证明 gcc 和甲言是不同的编译器。


## 四、为什么 V1==V2==V3 以前是必须的

历史原因。早期自举的时候，甲言版编译器刻意对齐 gcc 的输出：

```
早期 (v79→v92):
  甲言编译器刚诞生。
  为了证明"不是套壳"，要求 V1==V2==V3 全等。
  这意味着甲言的代码生成器要逐字节复制 gcc 的输出。

  代价很大：
  - struct 对齐要跟 gcc 完全一致
  - double 的 ABI 要跟 gcc 一模一样
  - 函数调用的栈帧布局要复制 gcc
  - gcc 改了版本，你的不动点就炸了

  这是用枷锁换证明。
```

后来发现不需要。V2==V3 就够了。

四条全绿。这就是甲言的闭环。


## 八、自举证明的工业标准

业界怎么验证编译器自举：

```
TinyCC (Fabrice Bellard):
  gcc编译tcc → tcc编译tcc → 产物对比。
  不要求跟gcc产物逐字节相同。只要求tcc能复制自己。

GCC:
  gcc-13编译gcc-14源码 → 产物A。
  gcc-14编译自己 → 产物B。A!=B 但都正确。
  不要求跨版本逐字节相同。

Rust:
  rustc (旧版) 编译 rustc源码 → 产物A。
  rustc (A) 编译 rustc源码 → 产物B。
  B==后续所有版本 → 自举闭环。
  不要求跟旧版编译器产物相同。
```

工业标准：V2==V3==V4... 自举闭环。V1==V2 从来不是要求。
甲言之前做到了 V1==V2 是因为刻意对齐——那是额外的努力，不是必须的标准。
