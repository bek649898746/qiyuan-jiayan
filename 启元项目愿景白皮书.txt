【摘要】

让语言回到语言本身。

启元项目已完成：让每一个不会英文的中国人, 都能用自己的母语
学会编程、用上 AI。

我们建造了中文编程的完整底层 —— 从中文汇编器到甲言C编译器,
全部自举（用自己编译自己）, 并以可验证的科学证据证明:
中文工具链与英文工具链语义完全等价。

我们追求的不是"能用"，而是"可证"：
每一次自举都有哈希为证，每一次对齐都逐字节可查。

不是"简化版", 不是"玩具", 不是"套壳"。
是 0 和 1 说中文。


===============================================================
【一、为什么做这件事: 一道真实存在的门】

1.1 编程世界默认说英文, 但 0 和 1 不认英文

机器码只有操作码和操作数, 全是数字, 没有任何语言属性。
"编程必须用英文"是历史偶然（美国起源、ASCII、生态锁定）,
不是技术必然。既然助记符可以是 MOV, 凭什么不能是"移动"?

1.2 语言门槛, 拦住了大多数人

中国有十几亿人, 会用英文编程的是极少数。
不会英文的人面对代码, 就像面对一堵墙:
看不懂、改不了、验证不了, 只能把控制权交给别人。

1.3 AI 时代, 墙没有消失, 反而变高了

大厂都在用 AI 写代码, AI 默认输出英文。
不会英文的人求 AI 写程序, 得到的是看不懂的英文代码——
他们可以"让 AI 写", 但无法"看懂、修改、验证"。
数字鸿沟从"不会编程"升级为"被 AI 代写"。

1.4 动机的起点

项目发起人郑宇和在推进公益"AI英语导师"（服务乡镇孩子）时反思:
教孩子翻墙, 教得再好, 墙还在。
为什么一定要英语? 于是开始研究甲言 —— 把墙拆了。

【二、已完成的交付成果】

2.1 甲言C编译器

  40 条中文关键字（整/字/若/主/输出...）
  自举不动点：GEN1==GEN2==GEN3 SHA256 完全相同
  零外部依赖，直出 x86-64 PE 可执行文件
  128 测试用例验证通过
  当前仅支持单文件编译（链接器推进中，暂不支持多文件联合编译）

  这意味着什么？

  甲言编译器编译自己，产生的二进制，
  和用 C 编译器编译它产生的二进制，**一个字节都不差**。

2.2 中文汇编器 (asm_zh)

  235 条中文助记符（压栈/移动/为零跳/浮加...）
  第二代自举不动点：自己汇编自己
  可独立于任何英文工具链运行
  完整 PE 写出器，支持 SSE 浮点、IAT 导入表

2.3 三级中文栈

  甲言C 源码 → 中文汇编文本 (.asm) → x86-64 真 PE (.exe)
  中文汇编文本作为项目专属底层中间文本，承担分层解耦作用
  每一层都能被人看懂、被 AI 读懂、被哈希验证

2.4 H1==H2 等价证明

  三级栈产物 SHA256 == 直发机器码 SHA256
  逐字节一致，分层零信息损失
  中文工具链与英文工具链 —— 数学上等价

  别人可以质疑"你用了 gcc"，
  但我们有哈希：三代产物同一个值。
  别人可以质疑"你的编译器是黑箱"，
  但我们有源码：中文写的，人人都能读。

  这就是确定性。这就是自证。

2.5 全链自治闭环

  编译器自举 ✅ | 汇编器自举 ✅ | 等价证明 ✅
  四条验证链全部通过
  两代不动点稳定可复现

  不依赖外部编译器 —— 自己写编译器
  不依赖外部语言 —— 用中文写编译器，用中文思考

  我们相信：一个真正"出生"的系统，
  必须能在孤岛上重新长成自己。

2.6 双重验证方法论

  两条独立路径编译同一份源码 → SHA256 比对
  任何编译器隐式 bug 当场现形
  适用于所有编译器的通用质量检测框架

2.7 共生生态

  ABI 兼容 Win64 标准，甲言可直接调用任何 C 编译的库
  整个 C 生态即是甲言的生态。不抢地盘，扩地盘

2.8 链接器（已完成，2026-08-04）

  jyld：自研 COFF 链接器（链接甲言与 C 的对象/静态库）
  qcc -c：甲言编译出标准 COFF 对象（重定位 + 符号表）
  jycc：驱动一步构建  jycc main.c lib.c -o app.exe
  与 C 生态完全互通：ABI 一致，链接 C 库（.a/.lib）
  验证：跨文件函数 / 静态变量+初始化 / 字符串 / printf 全部跑通
  直发路径 128/128 零回归，自举不动点保持

2.9 LoongArch 交叉编译验证（2026-08-04，严格边界）

  验证内容：甲言写的 C 源码 → 龙芯 gcc 交叉编译 → LoongArch ELF → QEMU 跑通
  （递归下降求值、结构体符号表、数组、指针、字符串哈希全部正确）

  验证层级（必须明确，不可混同概念）：
    ✅ 源码级交叉编译验证 —— 指令生成、ABI 对齐、ELF 构建
       全部由龙芯 GCC 完成；甲言仅提供符合自身语法规范的源码，
       不涉及自研编译后端。
    ⬜ 不等同于"甲言编译器原生支持龙芯" —— 距离甲言直出
       LoongArch 机器码、中文汇编器原生支持龙芯、全链路自举，
       仍有完整后端重写的工作量，二者技术层级不同。
    ⬜ 当前为 QEMU 用户模式模拟验证，未在龙芯真机落地，
       未完成系统调用、性能、异常处理的深度适配。

  复现：tests/loong/（源码 + 一键脚本 + 预期哈希），WSL+QEMU
  跨平台回归测试基准，任何人 clone 后一条命令复现。

【四、战略: 共生, 而非替代】

4.1 为什么对标 C

  编程语言四十年, 想"替代" C 的都死了, 寄生 C 的都活了。
  启元选择与 C 生态共生:
  底层共生: x86-64 + PE + Win64 ABI
  库层共生: ABI 相同, 直接调 C 库
  源码层共生: lexer 映射, 英文 C 代码即甲言资产

4.2 平台的延伸

  中文汇编文本作为独立的底层中间表示层，
  让造一门中文语言的门槛从编译原理专业级降到普通工程级。
  所有中文语言共享同一个底座 —— 既统一, 又多元。

  当前平台目标为 x86-64 Windows PE，
  国产 CPU 第一步已完成（LoongArch 交叉编译验证，2026-08-04），
  真原生（甲言直出 LoongArch/ARM64 机器码）为后续完整后端工作。

4.3 确定性优势

  本工具链提供编译结果的可验证性：
  H1==H2 双重验证使产物正确性可被数学证明。
  当前仅支持 Windows x86-64 平台，
  工业级安全场景（自动驾驶/医疗/金融）需额外适配验证。
  但方法论本身已提供传统工具链无法提供的安全保证。
