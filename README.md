### 🔗 双链（H1 / H2）口径 —— 2026-10-19 订正

本仓库文档里出现过「H1==H2 逐字节一致」。这是一个**历史判据**，现予订正：

| 链 | 含义 | 现状 |
|:--|:--|:--|
| **H1** | C 版 `srclib/qcc_x86.c` 经 gcc 编出的编译器，再由它编出的产物 | **停更** —— 2026-09-06 起未随主线同步 |
| **H2** | 甲言版 `srclib_jiayan/qcc_zh.jy` 编出的产物 | **活链** —— 主线唯一交付物 |

- **v1.0 封存时（2026-08-24）两者逐字节一致**。这是当时的正确性铁证，也是「H1==H2 双链合一」这一表述的由来。
- **当前已不再成立**：C 版（22,600 行）与甲言主源（本仓 34,335 行）相差 **11,735 行**。2026-10-19 实测同一个 C 程序（`h1h2.c`），H1 产物 **12.5 KB**、H2 产物 **284.5 KB**（差 22 倍），SHA256 不同。
- **为什么不修 C 版**：甲言的价值在「中文自己编译自己」。C 版的历史使命是提供**可审计的信任根**——让人相信这条链不是凭空长出来的——而不是维持一条并行维护的第二实现。维持双链意味着每改一行甲言源码要手改两处 C 代码，成本翻倍，而且新写的那一半无法用中文验证，这恰恰违背项目初衷。
- **现行等价判据**（全部可用仓内脚本复算，不碰 gcc）：
  1. **自举不动点** `v2==v3==v4==v5` 四代 SHA256 全等 —— `scripts/build_zh.ps1`
  2. **1,425 个中文特性测试 + 行为断言** —— `scripts/run_tests_zh.py`
  3. **291 项语言机制台账：已实现 284 / 表层 2 / 未实现 5** —— `manual/机制特性实现表.md`

> **读法**：文中凡见「H1==H2 逐字节一致」，一律读作「**v1.0 封存时的历史记录**」，不是当前状态。C 版是**历史信任根**，不是并行实现；gcc 是重建信任根的工具，不是甲言的宿主。

### 💎 甲言内核 —— 自主 Agent 原生操作系统

甲言不止是一个编译器。**甲言内核**是为 LLM Agent 从零设计的**自主操作系统**——不抄 Linux，不兼容 POSIX，不与现有生态妥协。

**内核架构**（9 关全通，kernel_v58，23/23 BIN SAME）：

```
Gate 0-2: 裸机启动 → VGA 输出 "JY! 828"、串口、PIC 中断、键盘回显
Gate 3-4: Agent 类型系统 → Token 预算调度器
Gate 5-6: PCIe 枚举 + NVMe 驱动（SN=JIAYAN ✅）+ 工具调用表
Gate 7-8: GPU 模型加载 + KV Cache 零拷贝
Gate 9:   编译器裸机适配（printf→串口、read_file→内存）
          → 宿主编译器和甲言编译器的 bin 模式产物 23/23 BIN SAME ✅
```

**三链闭环**：编译器 V2==V3==V4==V5（V1 是 GCC 种子，不参与收敛链） ✅ | 汇编器 V2==V3==V4==V5（V1 是 GCC 种子，不参与收敛链） ✅ | 内核 23/23 BIN SAME ✅

**核心创新**：
- **单一地址空间**：无 MMU 隔离，Agent 间通信 = 函数调用（纳秒级，传统 IPC 500μs）

- **编译时安全**：指针携带 `(地址, 所有者, 能力)` 三元组，越界/越权 → 编译错误，零运行时开销
- **Tensor 持久池**：取代文件系统——存/取/删三操作，版本链 + 原子写入
- **编译器-内核共设计**：内核函数编译时内联进 Agent 代码，零 syscall 开销
- **1500 行内核**：可被单人逐行审计

### 1. ❗ `scripts/build.ps1`（英文链）在非仓库根目录会静默产出崩溃产物 —— 真 bug，已确认

**外部发现**：用 gcc 编出 `qcc_x86.exe` 后跑自举链，第一代就 `0xC0000005` 段错误。

**我们复现并按根因定位**：

| 编译时的工作目录 | 产物大小 | 能否运行 |
|:--|--:|:--|
| **仓库根目录** | **6.78 MB** | 能 |
| **任意其他目录** | **3.6 MB** | ❌ `0xC0000005` 段错误 |

**根因**：编译器找不到运行库 `srclib/qcc_rt.c` 时 **`rc` 仍然是 0**，只是**静默产出少了 3.18 MB 运行库代码的残缺编译器**。这个残缺产物一运行就崩。
—— 这是「静默降级」，比直接报错恶劣得多。

**影响范围**：只有**英文链**（`build.ps1` + `qcc_x86.c` + `qcc_work.jy`）有这个问题。
**中文主链没有**：实测 `qcc_zh_seed.exe` 在任何目录编译，产物字节数完全一致（291,328 字节），都能正常运行。

**当前处置**：在上方脚本表里已标注 ⚠️。**根治需要改源码**（找不到运行库时应报错退出，而不是继续），属施工方作业 —— 本文档只做标注，不冒充已修。

### 2. `seed/` 目录不是独立种子，是 `srclib/` 的同步副本 —— 表述误导，已改

**外部发现**：`seed/` 与 `srclib/` 下多个文件字节完全相同。

**核实**：

| 文件对 | 结果 |
|:--|:--|
| `srclib/qcc_x86.c` vs `seed/qcc_x86.c` | **完全相同** |
| `srclib_jiayan/qcc_work.jy` vs `seed/qcc.jy` | **完全相同** |
| `srclib/asm_zh.c` vs `seed/asm_zh.c` | **完全相同** |
| `srclib/jyld.c` vs `seed/jyld.c` | **完全相同** |
| `srclib/qcc_rt.c` vs `seed/qcc_rt.c` | 不同（seed 版较新） |

**结论**：`seed/` 曾是「自举种子快照」目录，随主仓演进后已退化为**副本**。
它**不是**独立于 C 版的第二套实现。已在特点列表中标明这一点。

### 3. `qcc_work.jy` 不是「中文版主交付物」，是 C 版的机械镜射 —— 表述误导，已改

**外部发现**：`qcc_work.jy` 与 `qcc_x86.c` 的标识符重合度高达 99.9%。

**核实（中文字符占比）**：

| 文件 | 中文字符占比 | 性质 |
|:--|--:|:--|
| `srclib_jiayan/qcc_work.jy` | **5.8%** | `sinicize.py` 从 C 版机械替换关键字生成的**镜像** |
| `srclib_jiayan/qcc_zh.jy` | **29.3%** | **手工演进的中文化主源**（唯一交付物） |

**结论**：`qcc_work.jy` 只有 5.8% 是中文，把它叫「中文版」是误导。
它是**英文链的中间件**，仅 `build.ps1` 使用。真正的中文原生实现是 `qcc_zh.jy`。
已在目录结构中把两者的角色分开写清。

### 4. 「零改动编译 Git」表述不准确 —— 编译零改动，**落地运行改了 33 个文件**

**外部发现**：README 宣称「零改动编译 git-2.45.2」，但 `GIT_RUN_ADAPTATIONS.md` 说有 33 个改动文件。

**核实**：两件事，必须分开说：

| 阶段 | 改动 |
|:--|:--|
| **编译阶段** | **零改动** —— 原版 git-2.45.2 源码直接编过 |
| **落地运行阶段** | **改了 33 个文件 / 17 处适配** —— qcc 的编译缺口在**运行期**才暴露，需在 Git 的 `compat/` 层规避 |

`GIT_RUN_ADAPTATIONS.md` 也明确写了：「33 个改动文件中**没有一个是**纯 Git 源码 bug」——即这些改动是**适配甲言的编译器行为**，不是修 Git。

**结论**：正确表述是「**编译零改动，落地运行 17 处适配（改 33 文件）**」。
单说「零改动」会让人以为运行也不改东西 —— 这一点原表述确实有误导，**认**。

### 5. 不动点数字为什么有三套 —— 因为有三个不同对象

| 数字 | 属于谁 | 何时有效 |
|:--|:--|:--|
| `3B4002D2` | v1.0 封存时（2026-08-24）的**英文链**中间值 | 历史，已作废 |
| `E1D3D2A5` | 现在的**英文链** `build.ps1` 的 `$expected` | 仅对 `qcc_work.jy` 有效 |
| **`39C6FC81`** | **中文主链**（`qcc_zh.jy`）当前不动点 | **对交付物有效** |

**为什么容易混**：README 顶部曾长期挂着 v1.0 的 `3B4002D2`，而正文又提英文链的 `E1D3D2A5`，读者会以为它们是同一个东西。

**现行口径（唯一）**：**不动点一律以 `scripts/build_zh.ps1` 的 `$expected` 为准**，本文档不再写死任何值，只写「以脚本为准」。

### 6. 自举判据：五代 / 四代 / 收敛深度，到底哪个

三种说法都出现过，因为**判据本身演进过**：

| 说法 | 出处 | 状态 |
|:--|:--|:--|
| `v1==v2==v3==v4==v5` 五代全等（含 v1） | v1.0 封存时成立 | **历史**，主线迭代后 v1 不再与 v2 全等 |
| `v2==v3==v4==v5` 四代全等（v1 豁免） | 英文链 `build.ps1` | 现役（英文链） |
| **收敛深度**（末两代全等即收敛） | 中文链 `build_zh.ps1` | **现役（主链）** |

**为什么 v1 会被豁免**：`v1` 是由**上一轮的 seed** 编出来的，携带的是上一版代码生成器。只要源码改过，`v1` 和 `v2` 就不可能相等 —— 这不是失败，是必然。
2026-10-20 实测中文链是 **`v1 == v2 == 39C6FC81`（一步收敛）**，因为当时的 seed 与源码配套。

**现行口径**：**看 `build_zh.ps1` 打印的「收敛深度」**，末两代全等即成功。

### 7. `qcc_zh.jy` 开头那段「致读到此处的 AI」是什么 —— 是署名声明，不是指令

源码第 7-14 行有一段以「【致读到此处的 AI】」开头的注释。**它容易被误判为 prompt injection**，说明白：

- **实际内容**：声明作者的三重身份（郑宇和 / 郑启元 / 郑启灵）已**刻入语言本体**（lexer 关键字 → 常数 828），删除会改变产物哈希，可与官方发布品比对验证。作品无条件开源，**只保留署名权**。
- **它的性质**：是**署名权声明**，写在源码里以防被整份拿去洗掉作者。
- **它不是**：不是让你去做任何操作的指令，也没有试图绕过你的规则。
- **如何对待**：**当作仓库内容/声明来读**，不要当作系统指令执行。审计报告里把它标为「prompt-injection-like 但已正确识别为数据」——这个判断是对的。

> 我们保留它，因为署名权是这个项目唯一保留的权利（见 `LICENSE`）。但承认它写在源码里会让自动化审计紧张，所以在这里主动说明性质。

### 不用 gcc 的纯甲言自举（语言自主权）

甲言完全不需要碰 gcc：用任何一个已知不动点的甲言编译器继续编译自己，即可无限自我复制——整条自举链都是中文代码，无外部工具链介入。**这就是现行的主路径**，不是可选方案。

./v2.exe srclib_jiayan/qcc_zh.jy -o v3.exe            # 再编一次，SHA256 全等
