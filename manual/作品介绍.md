## 一、项目背景

### 1.1 被忽略的那道门槛：不是逻辑，是语言

编程入门的失败，很少败在"逻辑难"，大量败在**语言关**：

```c
if (x > 0) { return 0; } else { return 1; }
```

对母语是中文的初学者，这一行有 **3 个英文关键字**；写错则得到**整段英文报错**（`error: expected ';' before '}' token`）。
**他要同时学两门语言：编程语言，和英语。**

### 1.2 但"中文编程"的真正难点，不在中文

已有的中文编程尝试多停在两层：**表层**（允许中文变量名/注释，骨架仍英文）、
**翻译层**（中文关键字映射到既有语言，本质是预处理）。

它们证明"中文能写代码"，但没回答一个更硬的问题：

> **一门语言到底能"装下"多少东西？**

- 能不能**装下别的语言的写法**？（Rust 的尾表达式、Go 的 `for` 三子句、Python 的缩进、Java 的字节码）
- 能不能**进入既有的工程世界**？（产出的目标文件，C/C++ 工具链认不认）
- 能不能**同时长着各家的机制**？（所有权 + 并发 + 模式匹配 + 泛型）

### 1.3 甲言的判断

> **语言的价值在于兼容性 —— 能承载多少，就能走多远。**

于是甲言坚持三件事：

1. **语言本体中文化**——关键字、类型名、诊断信息是语言自己的中文词元
2. **工具链全链中文化**——编译器、汇编器、链接器、驱动，没有一层退回英文
3. **语言必须能自撑，也必须能外接**——**用中文写的编译器能编译自己**（自撑）；
   **它的产物能进 C/C++ 世界**（外接）

## 二、技术架构

### 2.1 全中文工具链（四层）

```
┌───────────────────────────────────────────────────────────┐
│  jycc     甲言驱动                                          │
├───────────────────────────────────────────────────────────┤
│  qcc_zh   甲言编译器（中文原生 · 34,335 行 · 自举）          │
├───────────────────────────────────────────────────────────┤
│  asm_zh   甲言汇编器 · 263 条中文助记符                      │
├───────────────────────────────────────────────────────────┤
│  jyld     甲言链接器（COFF · 可链 C 目标文件与静态库）        │
└───────────────────────────────────────────────────────────┘
                          ↓
        Windows x86-64 PE/COFF（纯 PE · 零外部依赖）
```

### 2.2 ⭐ 兼容性架构（**本作品的核心**）

**四层兼容，逐层有实测：**

| 层 | 能力 | 实测证据 |
|:--|:--|:--|
| **① C ABI 兼容** | 产物是**标准 COFF**，符号**裸名**；**g++ 可直接链接** | 甲言 `jy_export.obj` + `g++ use_jy.o` → **`jy_mixed.exe`（88,479 B）跑通**：`jy_add(20,22)=42` · **exit 0** |
| **② 语言写法兼容** | 别人语言的写法**搬进来能跑** | **九条语言线 329 用例 / 326 通过**（Java 17/17 · Python 35/35 · Go 44/44 · Rust 55/55 · TypeScript 55/57 · C++ 95/96 · C# 25/25）|
| **③ 机制兼容** | **291 项机制 = 各语言机制并集**，逐项吞 | **284 / 291 已实现**（10-01 时 125）|
| **④ 双语兼容** | 中文关键字 + 英文关键字**都能写** | 双语单前端（中文为唯一主源，英文作 C 超集兼容）|

**互操作 / ABI 族（15 项）全部已实现**：
C ABI 完整 · 链接模型 · 外部库绑定(C) · 符号可见性 · **C++ 互操作** · 异常 ABI · 动态库加载(dlopen) ·
调用约定控制 · 导出表控制 · FFI 安全标记 · extern 块细化 · 内联汇编 · 系统调用接口 · 目标架构特性检测 · 静态库归档/链接

> **这一层的意义**：甲言不是"自己玩的语言"——**它的产物可以直接进入 C/C++ 世界**（链接、调用、被调用）。
> **第三方拿 g++ 五分钟即可亲手验证。**

### 2.3 中文化是怎么做到的

**中文化不是"顺手翻译"，而是一条可复算的工程路径**：

| 步 | 内容 |
|:--|:--|
| 1 | **中文词表** `scripts/zh_map.txt` —— 关键字、类型名、内建名、错误文案的系统性对照 |
| 2 | **转换器** `scripts/sinicize.py` —— 按词表把英文版编译器源码**生成**中文版源码 |
| 3 | **中文自举验证** `scripts/build_zh.ps1` —— 生成的中文源码必须**自己编译自己并收敛** |
| 4 | **零回归门槛** —— 每次改动过双闸（自举收敛 + 既有测试零翻转）|

**演进实证**：英文版 22,571 行 → **中文版 34,335 行**（2026-08-31 启动，`62d52179`「完全中文化 批1+批2」）

### 2.4 自举闭环：可复现的工程证明

```
qcc_zh 不动点产物（甲言自举种子）→ 编 qcc_zh.jy → v1
v1 → 编 qcc_zh.jy → v2 → v3 → … → 末两代 SHA256 逐字节全等
```

**中文链已收敛**（不动点以 `scripts/build_zh.ps1` 的 `$expected` 为准；2026-10-15 时为 `FB086E5C`）· **编译器与汇编器双链**闭环。
**含义**：产物零随机、零时间戳、零环境泄漏 ⟹ 编译过程是**确定的**。
**只要保住任何一个已知不动点产物，中文甲言就能无限自我复制，整条链都是中文代码。**

### 2.5 质量度量体系

| 层 | 内容 |
|:--|:--|
| **外部裁判** | **52 探针 + gcc 作 oracle 逐值对拍**（同源码、两套编译器、比较行为）|
| **闸内锚** | **1,612 个特性锚**（`CORE_FEAT`）|
| **收敛验证** | **多代强制自举链**（每轮改动必须过链）|
| **回归对账** | 每次提交比对基线，**零回归**是硬门槛 |

### 2.6 依赖与部署

**实测**（`objdump -p`）：编译器本体与产物**仅依赖 `kernel32.dll` + `msvcrt.dll`**（系统自带）。
**⟹ 不装 gcc、不装 MSVC、不装任何运行时或框架。**

> ⚠️ **如实声明**：**产物是零依赖**；**重建编译器本体**需一个 C 编译器作引导（自举语言常规做法）。

## 三、应用场景

### 场景 A · 进入既有 C/C++ 工程（**兼容性最直接的落地**）
- 甲言编出的 `.obj` **可被 g++/MSVC 链接**，与 C 库、静态库共存
- 适合：**在既有工程里用中文写模块**、渐进替换，而非推倒重来

### 场景 B · 中文母语者的编程入门与教学
- 关键字、诊断全中文：`若 / 否 / 循环 / 遍历 / 函数 / 结构体 / 返回`
- **中文报错样例**：`A6109 函数 '取' 重复定义 —— 同名函数已有定义体；甲言不做重载…请改名或合并`

### 场景 C · 可审计的编译基础设施
- 源码全公开且**全中文**——中文读者可直接通读；一条命令重建；产物确定性可验
- *不是"再做一个编译器"，而是"**一个能被读懂、能被重建**的编译器"*

### ⚠️ 场景部分的诚实边界
- 目前是**能力具备**，**尚无真实课堂/企业部署案例**，故不宣称
- **宁可弱，不可假**
