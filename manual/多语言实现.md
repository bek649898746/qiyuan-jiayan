# 甲言 · 多语言实现（九条语言线）

> **一句话**：用**甲言**（中文关键字语言）写了**九种语言**的解释器 / 编译器前端，并逐例验收。
>
> 📖 **本页讲「做出了什么」（成果）**；**「怎么写」见姊妹篇 [`多语言实现方法.md`](多语言实现方法.md)**
> （19 条可复用手法 · 指令集跨线累积 · 3 条方法论教训 · 6 条流程铁律）。

**为什么这是硬指标**：一门语言能不能干活，不看能否编译 hello world，
而看**能不能实现别的语言**。本页 2026-10-15 由启元整理，素材为九条线的实测报告（合并总账 469 行）。

## 二、⚠️ 验收口径与局限（**这一节比数字更重要**）

我们**不把「全绿」包装成「与官方完全一致」**：

| # | 局限 | 说明 |
|--:|:--|:--|
| 1 | **无官方编译器交叉对照** | 本机**没有 JDK / Go / Rust / TypeScript / C++ / C# 任何一条工具链**。七条线的正确性依靠**逐字节手验字节码 + 自建 VM 执行**，**不是**由官方编译器判定的 |
| 2 | **「全绿」的确切含义** | = **在本套判据下全绿**，**不等于**「与官方行为一致」 |
| 3 | **JS / JV 两线较弱** | 无独立定稿报告、无精确计数 ⟹ 总账中这两行**弱于其余七行** |
| 4 | **C# 与 C++ 内核不同源** | C# 线把对象变量由**值语义**改为**引用绑定**，而 C++ 线已投递未回改 ⟹ **此差异属未结项**，如实记录 |

> 口径原则：**能核验的说不清就能核验**，不能核验的说清边界 —— 见 [`数据口径与核验方法.md`](数据口径与核验方法.md)。

## 三、跨语言价值（这才是做这件事的真正意义）

九条线摊开后，**同一维度上各语言的分歧**反而成了甲言的测试用例：

| 维度 | 九线的分歧 | 甲言的处理 |
|:--|:--|:--|
| **语句分隔 / 块结构** | Python：换行 + **缩进**；Rust：**分号**、换行完全无意义（两者正相反） | INDENT / DEDENT **直接当块括号**用；Rust 侧按分号成句 |
| **调用回填** | 九线共识：函数体先编、调用地址后填 | **两阶段回填**（先编完所有函数体，再统一回填）—— 此坑只犯过一次 |
| **作用域槽命名** | C++ / C# 暴露最狠（全局槽按名复用） | 隐藏槽用 `#` 前缀（`#` **不是合法标识符首字符** ⟹ 用户代码永远撞不上，无需转义） |
| **类型检查时机** | Rust / TypeScript 在**编译期**；其余在运行时 | 甲言**两者都能承载**（TS 线每例打印「变量 → 类型」表，故"通过"不是碰巧） |
| **类型系统范式** | Java/Rust 名义类型（靠名字） vs **TS 结构化类型**（靠形状） | 均已实现（`Point{x,y,z}` 兼容、字段顺序无关、`Point` 与 `Line` 不兼容） |
| **对象模型** | C++ **值语义** vs C# **引用绑定** | **九线里唯一互相冲突的维度**（未结项，已如实记录） |

**结论**：甲言不只"能用中文写程序"，它**能承载九种语言的语义分歧** ——
这比任何单个 demo 都更能说明它的表达力边界。
