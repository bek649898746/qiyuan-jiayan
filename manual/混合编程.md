# 混合编程：甲言框架 + C 热点

甲言可以直接调用 C 函数：把 C 源码用 `gcc -O2` 编成 `.o`，甲言源码用 `qcc -c`
编成 `.o`，再由 `jyld` 链接成一个可执行文件。这是**已经跑通**的路径，不是规划。

## 什么时候值得混合

- 循环密集、数值计算、矩阵/向量运算：C + `gcc -O2` 目前更快；
- 已有 C 库/驱动：不必重写，直接链接；
- 业务框架、错误处理、并发调度：用甲言，类型与诊断更省心。

## 三步流程

```powershell
# ① C 热点
gcc -O2 -c hot.c -o hot.o

# ② 甲言框架（注意：-c 必须显式带 -o）
qcc_zh_seed.exe -c app.jy -o app.o

# ③ 链接 + 运行
jyld.exe app.o hot.o -o app.exe
.\app.exe
```

最小完整示例见 `examples/interop/`，一键脚本 `build.ps1`。

## 常见错误

### 1. `qcc -c` 不带 `-o`

`-c` 表示「产出目标文件」，但不指定 `-o` 时仍走默认输出名（可能得到 `a.exe`）。
**`qcc -c` 必须带 `-o`**：写 `qcc -c app.jy -o app.o`，否则可能得到默认输出名（如 `a.exe`）。

### 2. 声明了外部函数，但忘记链接对应 `.o`

修前行为是**静默返回 0**；现在 EXE 模式会响亮失败：

```
[ERR] A6100 未定义的外部符号 'hot_add' —— 已声明但本编译单元无定义；
      分模块请用 -c 编译后由链接器解析，单文件请提供定义或链接对应 .o
```

`-c` / `-S` 模式仍允许未解析符号（因为要等链接），这是分模块编译的正常形态。

### 3. 参数类型对不上

甲言的 `整` 是 4 字节，`长整` / 指针是 8 字节；C 侧签名要与甲言声明逐项对齐。
结构体跨语言传递时，先用 `大小(构 X)` 与 C 的 `sizeof` 对照一次。

## 性能建议

- 热点函数放 C，用 `gcc -O2`；调用边界越少越好（一次传数组/结构体，别在循环里反复跨语言调用）。
- 甲言侧负责分配、生命周期与错误路径；C 侧只做纯计算。
- 先用 `QCC_OPT=all` 编甲言侧，再对比整体耗时；不要凭感觉把整段逻辑搬去 C。
