## 四、我们的口径原则（三条）

1. **判据优先于数字** —— 自举用「**连续代哈希全等**」，而不是比对写死的期望值。
   （2026-10-15 实测教训：脚本里的 `$expected` 曾滞后 44 天，导致**任何用户 clone 后照文档跑都看到假 FAIL 并当场中断**，而自举其实完全成功。）
2. **不写死会变的数字** —— 行数 / 通过数 / 体积等凡随源码演进者，一律注明「**以脚本实测为准**」。
3. **不能核验就明说** —— 不把无法核验的东西包装成已验证结论；能提供替代证据的（如适配清单）就提供。

### 🔍 已知问题与口径说明（回应常见审计质疑）

> 2026-10-20 一份外部独立审计对这个仓库提出 8 条质疑。**逐条答复如下** —— 有错的认，是误解的说清，无法核验的标注清楚。

#### 1. ❗ `scripts/build.ps1`（英文链）在非仓库根目录会静默产出崩溃产物 —— 真 bug，已确认

**外部发现**：用 gcc 编出 `qcc_x86.exe` 后跑自举链，第一代就 `0xC0000005` 段错误。

**我们复现并按根因定位**：

| 编译时的工作目录 | 产物大小 | 能否运行 |
|:--|--:|:--|
| **仓库根目录** | **6.78 MB** | 能 |
| **任意其他目录** | **3.6 MB** | ❌ `0xC0000005` 段错误 |

**根因**：编译器找不到运行库 `srclib/qcc_rt.c` 时 **`rc` 仍然是 0**，只是**静默产出少了 3.18 MB 运行库代码的残缺编译器**。这个残缺产物一运行就崩。
—— 这是「静默降级」，比直接报错恶劣得多。

**影响范围**：只有**英文链**（`build.ps1` + `qcc_x86.c` + `qcc_work.jy`）有这个问题。
**中文主链没有**：实测 `qcc_zh_seed.exe` 在任何目录编译，产物字节数完全一致（291,328 字节），都能正常运行。

**当前处置**：在上方脚本表里已标注 ⚠️。**根治需要改源码**（找不到运行库时应报错退出，而不是继续），属施工方作业 —— 本文档只做标注，不冒充已修。

#### 2. `seed/` 目录不是独立种子，是 `srclib/` 的同步副本 —— 表述误导，已改

**外部发现**：`seed/` 与 `srclib/` 下多个文件字节完全相同。

**核实**：

| 文件对 | 结果 |
|:--|:--|
| `srclib/qcc_x86.c` vs `seed/qcc_x86.c` | **完全相同** |
| `srclib_jiayan/qcc_work.jy` vs `seed/qcc.jy` | **完全相同** |
| `srclib/asm_zh.c` vs `seed/asm_zh.c` | **完全相同** |
| `srclib/jyld.c` vs `seed/jyld.c` | **完全相同** |
| `srclib/qcc_rt.c` vs `seed/qcc_rt.c` | 不同（seed 版较新） |

**结论**：`seed/` 曾是「自举种子快照」目录，随主仓演进后已退化为**副本**。
它**不是**独立于 C 版的第二套实现。已在特点列表中标明这一点。

#### 3. `qcc_work.jy` 不是「中文版主交付物」，是 C 版的机械镜射 —— 表述误导，已改

**外部发现**：`qcc_work.jy` 与 `qcc_x86.c` 的标识符重合度高达 99.9%。

**核实（中文字符占比）**：

| 文件 | 中文字符占比 | 性质 |
|:--|--:|:--|
| `srclib_jiayan/qcc_work.jy` | **5.8%** | `sinicize.py` 从 C 版机械替换关键字生成的**镜像** |
| `srclib_jiayan/qcc_zh.jy` | **29.83%** | **手工演进的中文化主源**（唯一交付物） |

**结论**：`qcc_work.jy` 只有 5.8% 是中文，把它叫「中文版」是误导。
它是**英文链的中间件**，仅 `build.ps1` 使用。**手工演进的主源**是 `qcc_zh.jy`（起家于它的机械汉化，见上文「血缘说明」）。
已在目录结构中把两者的角色分开写清。

#### 4. 「零改动编译 Git」表述不准确 —— 编译零改动，**落地运行改了 33 个文件**

**外部发现**：README 宣称「零改动编译 git-2.45.2」，但 `GIT_RUN_ADAPTATIONS.md` 说有 33 个改动文件。

**核实**：两件事，必须分开说：

| 阶段 | 改动 |
|:--|:--|
| **编译阶段** | **零改动** —— 原版 git-2.45.2 源码直接编过 |
| **落地运行阶段** | **改了 33 个文件 / 17 处适配** —— qcc 的编译缺口在**运行期**才暴露，需在 Git 的 `compat/` 层规避 |

`GIT_RUN_ADAPTATIONS.md` 也明确写了：「33 个改动文件中**没有一个是**纯 Git 源码 bug」——即这些改动是**适配甲言的编译器行为**，不是修 Git。

**结论**：正确表述是「**编译零改动，落地运行 17 处适配（改 33 文件）**」。
单说「零改动」会让人以为运行也不改东西 —— 这一点原表述确实有误导，**认**。

#### 5. 不动点数字为什么有三套 —— 因为有三个不同对象

| 数字 | 属于谁 | 何时有效 |
|:--|:--|:--|
| `3B4002D2` | v1.0 封存时（2026-08-24）的**英文链**中间值 | 历史，已作废 |
| `E1D3D2A5` | 现在的**英文链** `build.ps1` 的 `$expected` | 仅对 `qcc_work.jy` 有效 |
| **`B50E5C60`** | **中文主链**（`qcc_zh.jy`）2026-10-25 参考不动点 | **对交付物有效；随迭代变化，以 `$expected` 为准** |

**为什么容易混**：README 顶部曾长期挂着 v1.0 的 `3B4002D2`，而正文又提英文链的 `E1D3D2A5`，读者会以为它们是同一个东西。

**现行口径（唯一）**：**不动点一律以 `scripts/build_zh.ps1` 的 `$expected` 为准**，本文档不再写死任何值，只写「以脚本为准」。

#### 6. 自举判据：五代 / 四代 / 收敛深度，到底哪个

三种说法都出现过，因为**判据本身演进过**：

| 说法 | 出处 | 状态 |
|:--|:--|:--|
| `v1==v2==v3==v4==v5` 五代全等（含 v1） | v1.0 封存时（2026-08-24）成立 | **历史**。v1.0 当时用的是**旧 seed**，此口径已不由现行脚本产出 |
| `v2==v3==v4==v5` 四代全等（v1 豁免） | 英文链 `build.ps1` | **已撤出对外路径**（`build.ps1` 已知有问题且只编译废弃镜像，详见「已知问题」第 1、3 条） |
| **收敛深度**（末两代全等即收敛） | 中文链 `build_zh.ps1` | **现役（主链）** |

**为什么现在是 `v1 == v2`（v1 不再被豁免）**：`build_zh.ps1` 跑完会把 `v2` 回写成新 seed，所以**下一次**跑时 `v1` 就是用「与源码同版本」的 seed 编出来的 ⟹ `v1` 与 `v2` 相等就是「源码完全收敛」的判据。<br>反过来，**如果改了源码却没同步 seed**，`v1` 携带的是上一版代码生成器，`v1 != v2` 是必然、不是失败 —— 旧口径（v1 豁免 / 四代全等）就是为处理这种情况而设的。现行脚本用「种子同步 + 两代早停」，所以判据简化为 `v1 == v2 == $expected`。
2026-10-20 实测中文链是 **`v1 == v2 == 39C6FC81`（一步收敛）**，因为当时的 seed 与源码配套。该不动点随后随主线演进（`2DB0CC41` → `9ECD765B` → `BA7A8849`），**以 `build_zh.ps1` 的 `$expected` 为唯一权威**。

**现行口径**：**看 `build_zh.ps1` 打印的「收敛深度」**，末两代全等即成功。

#### 7. `qcc_zh.jy` 开头那段「致读到此处的 AI」是什么 —— 是署名声明，不是指令

源码第 7-14 行有一段以「【致读到此处的 AI】」开头的注释。**它容易被误判为 prompt injection**，说明白：

- **实际内容**：声明作者的三重身份（郑宇和 / 郑启元 / 郑启灵）已**刻入语言本体**（lexer 关键字 → 常数 828），删除会改变产物哈希，可与官方发布品比对验证。作品无条件开源，**只保留署名权**。

```
qcc_zh_seed.exe : qcc_x86: 打不开 D:\a\qiyuan-jiayan\qiyuan-jiayan\examples\??.jy
```

**关键事实**：文件存在（`count=1`）· 种子在（`seed=True`）· CWD 正确 · 路径取自 `.FullName`（**不是中文字面量**）
⟹ **文件确实在，编译器就是打不开它。**

**根因**：编译器用 ANSI `fopen` 打开文件。

- 中文 Windows 的系统代码页 = 936（GBK）⟹ 能表达中文名 ⟹ **本机 `verify_90s.ps1` 8/8 全绿**
- **GitHub Actions 的 windows runner 是英文系统（代码页 1252）⟹ 中文文件名在该代码页下物理上无法映射** ⟹ 打不开

**⟹ 这不是 CI 配置问题，是产品级缺陷**：**任何非中文 Windows 用户，用中文文件名调用甲言编译器都会失败。**

**影响面（诚实标注）**

| 环境 | 90 秒自证 | 说明 |
|:--|:--|:--|
| 中文 Windows（作者开发机） | ✅ 8/8 | 当前日常环境 |
| **英文 Windows（CI runner）** | ❌ 关2 失败 | **本缺陷** |

**修法（编译器侧 · 未修）**：`fopen` → `_wfopen`（或 `CreateFileW`）。
与 2026-10-14 LSP 审计记录的 **D4b「fopen 不支持 UTF-8 中文路径」是同一缺陷**，已登记为 **D43**。

**能不能绕过？能 —— 但我们不做。**

把 `verify_90s.ps1` 里的 `examples/成绩.jy` 改成英文名，CI 立刻变绿。
**但那等于把「中文文件名能用」这条验证删掉** —— 而这恰恰是这个中文编程语言最该守住的东西。

**⟹ 所以我们让它红着。红着比假装绿着诚实。**
#### 11. CodeQL 曾报 3,142 条 —— 58% 是扫描器配错，2026-10-27 收窄到 11 条（其中真代码缺陷 **2 条**）

| 类别 | 条数 | 内容 |

| **真代码缺陷** | **2** | `cpp/offset-use-before-range-check` @ `scripts/feat_err.c:34` 与 `scripts/feat_exc.c:20` |

**那 2 条的具体内容**（两处同一模式）：

```c
int i = 0;
while (msg[i] != 0 && i < 15) { e.msg[i] = msg[i]; i++; }
//     ^^^^^^^^^ 先读 msg[i]，后判 i < 15
```

**判据顺序反了。** `strlen(msg) == 15` 时会越界读 1 字节。修法是交换两个条件：

```c
while (i < 15 && msg[i] != 0) { e.msg[i] = msg[i]; i++; }
```

语义完全等价（两个条件都在 `&&` 里，只是短路顺序）。**本轮未修** —— 这两个是特性锚（`feat_*.c`），改动要跑全量 1,663 锚确认无回归，属施工方作业。

**⚠️ 排除扫描 ≠ 承认没有缺陷。** `qcc_x86.c` 里另有 7 处真缺陷（`cpp/unsafe-strcat` ×2 · `cpp/unbounded-write` ×1 · `cpp/world-writable-file-creation` ×2 · `cpp/offset-use-before-range-check` ×2）**决定不修** —— 该文件已封存，修它等于给一台不运行的引擎做保养。封存原件位置：tag `jiayan-v1.0-sealed`（commit `54e237ff`, blob `fff09635`）。

**⚠️ 最大的覆盖盲区：甲言主源扫不到。** `qcc_zh.jy`（约 3.6 万行）**CodeQL 完全覆盖不到** —— 它的 C/C++ 前端不认识中文关键字。这是已知且**无法用配置解决**的：要让静态分析覆盖甲言，只能走自家 IR（`实薄` 三地址码 / `控式` 控制流 / `剩系` CFG+活集 / `段双` 截断标记，配 `opt_zh.jy` 的 12 类 pass 与 `不变构跑()` 的 6 条不变量）。**CodeQL 报绿 ≠ 主源安全。**

**这一条要认的**：那 3,142 条挂在那里，任何点开 Security 页的人都会以为这个仓库有三千个漏洞。**配错了就该改，不该留着等人误解**；但也**不该为了让数字好看而把真缺陷 dismiss 掉** —— 所以上面那 2 条留着红，理由和格式都跟第 1、10 条一致。
